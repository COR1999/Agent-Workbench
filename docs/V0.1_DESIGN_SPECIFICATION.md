# OPEN QUESTION DECISIONS

## Q1 — Is `hotsauce-mama` representative, or an outlier?

**RECOMMENDATION:** Design for both eras. Do not optimise for `hotsauce-mama`.

**EVIDENCE.**
- *[PROVEN]* Report 01 §2 documents two distinct working modes that both persist: Era 2 (nine repos, 3–52 commits, single branch, no PRs, 0–1 test files) and Era 3 (two repos, 179 and 474 commits, full PR/issue/CI discipline).
- *[PROVEN]* Era 2 includes real commercial work — `achara-dublin-website`, `quadWeb` ("basic website to show to customer"), `pierogalsWeb`, `gscWeb`. It is not throwaway practice.
- *[PROVEN]* Era 3 is the most recent work and `hotsauce-mama` is still open (PR #256 open, 24 open issues).
- *[INFERRED]* The trajectory 2019 → 2026 is one-way in sophistication, so future *product* work will look like Era 3. But nothing in the archaeology suggests you will stop taking small client sites.

**TRADEOFF.** Optimising for Era 3 gives you `sweep-the-class`, `audit-to-issues` and concurrency review — powerful, but they idle on a 5-commit brochure site. Optimising for Era 2 gives you `deslop` and lessons — useful everywhere, but under-serves the work that actually generates production bugs.

**DECISION.** Both, resolved by *sequencing rather than compromise*. Every v0.1 component must pass an **Era-2 adoption test**: can it be adopted by a 5-commit client site in under five minutes, and does it deliver value there? Lessons pass (they prevent the Windows/`next-og` and shadcn-pin mistakes on day one of any Next.js site). Deslop passes (report 03 Problem 10 measures slop concentrated *precisely* in Era-2 repos). Sweep-the-class passes weakly — it does less on a small site, but it costs nothing to have installed.

Anything failing that test is deferred to v0.2, which is why `audit-to-issues` is not in v0.1 despite having the highest single-invocation payoff in your history.

## Q2 — Publish the repo?

**RECOMMENDATION:** Don't decide yet. Adopt the discipline that keeps both options open.

**EVIDENCE.**
- *[PROVEN]* One of your two deep-evidence repos (`hotsauce-mama`) is private client work. Report 14 flagged that lessons derived from it touch brand direction, pricing decisions and an Instagram token workaround.
- *[PROVEN]* You maintain a portfolio (`ai-app`) and a personal site, and report 01 records interview/CV artefacts throughout your Desktop — publication has plausible value to you.
- *[CANNOT BE DETERMINED]* Whether you want to publish is a preference. The archaeology cannot answer it and I won't invent an answer.

**TRADEOFF.** Deciding "private" now costs nothing today but means retrofitting client-safety into every lesson later. Deciding "public" now forces a discipline you may not want. Deferring costs one habit.

**DECISION.** Build **client-safe by default from the first lesson**. Every lesson states the *technical* claim and the *cost*, with the source as a bare reference (`hotsauce-mama#249`), never with client context. Compare:

```
BAD:  Mama Amaya's product pages showed Jungle Sauce as Coming Soon...
GOOD: A destructured `error` that is never read makes a query failure
      indistinguishable from an empty result. Cost: a live product showed
      as unavailable on one route and available on another. (hotsauce-mama#249)
```

The second is more useful *as a lesson* anyway — it generalises. This makes the publish decision reversible and non-blocking. Revisit at ~20 lessons.

## Q3 — Which harnesses must this work in?

**RECOMMENDATION:** Make the valuable part harness-independent, and support two install targets for the rest.

**EVIDENCE.**
- *[PROVEN]* `~/.claude/` is active on your machine. `~/.codex/` exists on disk. Your portfolio's AI Tools list names Claude, Copilot, ChatGPT and Codex (report 01).
- *[PROVEN]* `~/.claude/` currently contains no `CLAUDE.md`, no `skills/`, no `commands/` — only 34 auto-accumulated permission entries (report 08). There is nothing to migrate.
- *[PROVEN]* Your `senus-board-report` already solves cross-harness context with a one-line `CLAUDE.md` containing `@AGENTS.md`.
- *[NOT VERIFIED]* Report 16 flagged that Windows symlinks are untested. Still untested — I was asked not to run scans, and this needs a real trial, not a scan.

**TRADEOFF.** Chasing every harness means a fragile installer. Picking one means the system dies if you switch tools.

**DECISION.** Split by risk:

- **Lessons and rules are plain Markdown inside the project** (`AGENTS.md`). Every agent reads them, no installation, no harness dependency, works in an editor with no agent at all. This is the majority of v0.1's value and it is **immune to the harness question**.
- **Skills install to `~/.claude/skills/` and `~/.agents/skills/`** via one script. If symlinks prove unreliable on Windows, the script copies and prints "re-run after `git pull`". Test this on day one and document what actually happened — do not ship an installer whose behaviour you assumed.

This is deliberately de-risked: if the skill install never works properly, you still have ~70% of v0.1's value.

## Q5 — Will you run skills that mostly report "nothing found"?

**RECOMMENDATION:** Stop treating this as a question about you and make it a design requirement.

**EVIDENCE.**
- *[PROVEN]* `hotsauce-mama` and `senus` are measurably clean (report 03 Problem 10: 5 and 2 narrating comments respectively, 0 `any`). Deslop will frequently find nothing there.
- *[PROVEN]* Your own standard for review output, from your scalability review: *"Every finding below traces a real request path through actual files in this repo (paths and line numbers included)."* You value demonstrated thoroughness, not just findings.
- *[INFERRED]* A skill that returns "no issues found" with no evidence of what it looked at is indistinguishable from a skill that did nothing. That is why such skills get abandoned — not because the user lacks patience.

**TRADEOFF.** Requiring a coverage statement makes every output slightly longer.

**DECISION.** **Every FIND-type skill must report what it searched, not only what it found.** A null result becomes positive evidence of coverage:

```
Searched 42 files under src/lib and src/app/actions for destructured
`error` bindings that are never read (pattern: `{ data, error }` + no
`if (error)` in scope). 3 candidates examined, 0 same-class. Clean.
```

That is a useful artefact. "No issues found" is not. This single rule is what makes `sweep-the-class` trustworthy enough to run habitually, and it costs two sentences.

# CORE MODEL

Eight concepts, each with a one-line definition and a **discriminating test**. The test matters more than the definition — it's what stops everything collapsing into "skill".

| Concept | Definition | Discriminating test | Lives in |
|---|---|---|---|
| **RULE** | Always true. No conditions, no procedure. | Can you state it without an "if"? Is violating it *always* wrong? | `AGENTS.md` (central = machine-wide; project = repo-wide) |
| **LESSON** | True **when a condition holds**. Learned at a cost. Can go stale. | Does it need an `applies-to`? Could a version bump make it false? | `lessons/*.md` (central), inlined into project `AGENTS.md` |
| **PROJECT CONTEXT** | True only in this repository. | Would it be false, or meaningless, in your next project? | Project `AGENTS.md` / `docs/` / `README.md` |
| **SKILL** | A repeatable procedure containing judgement. Has steps, guardrails, and a defined output. | Does it have steps? Would two runs on the same input produce the same *shape* of output but different content? | `skills/<name>/SKILL.md` |
| **TOOL / SCRIPT** | Deterministic. Same input, same output. No judgement. | Could you write it in bash and be confident it's correct? | `scripts/` |
| **WORKFLOW** | An ordered sequence of skills toward one objective. | Is it just "do A, then B, then C" where A/B/C are skills? | **Not in v0.1.** |
| **EXPERIENCE** | A structured record of what happened during one unit of work. | Is it about a *specific past event*, not a general truth? | Git commit bodies + PR descriptions (v0.1 uses what you already write) |
| **EVALUATION** | Evidence that a skill or change did or didn't work. | Does it compare a before and an after? | **Not in v0.1**, except deslop's fixtures |

## The three-way split that carries the whole design

The single most important distinction, because it is the mechanism of portability:

```
RULE             always true              →  no condition
LESSON           true when X              →  applies-to: [X]      ← the portable unit
PROJECT CONTEXT  true only here           →  never leaves the repo
```

*Example, from real archaeology findings:*

- "Never claim verified what you couldn't execute" → **RULE** (central `AGENTS.md`)
- "`next/og`'s `ImageResponse` breaks `next build` on Windows" → **LESSON** (`applies-to: [nextjs, windows]`)
- "No flames, skulls, or EXTREME HEAT language anywhere" → **PROJECT CONTEXT** (`hotsauce-mama` only)

Most systems fail by putting all three in one file. Report 13 showed your 49KB `CLAUDE.md` doing exactly that.

## The three flows

**Flow 1 — knowledge escaping the project that taught it**

```
PROJECT  →  WORK  →  EXPERIENCE  →  LESSON  →  next project
                     (commit body,   (lessons/*.md,   (inlined at init
                      PR, incident)   applies-to: X)   when X matches)
```

The gap the archaeology found is the third arrow. Everything before it already works in your practice — you write excellent commit bodies and incident notes. v0.1 builds only that arrow.

**Flow 2 — AI output**

```
AI OUTPUT  →  DESLOP  →  REVIEW
              (remove what's inconsistent with this file's own conventions,
               preserve information / safety / intent)
```

Deslop is a **filter, not a reviewer**. It does not find bugs. When it finds something that isn't slop, it hands off and says so.

**Flow 3 — change**

```
CHANGE  →  SWEEP-THE-CLASS  →  COVERAGE
           (characterise the shape,      (an inventory + an explicit
            search for siblings)          statement of what was searched)
```

Sweep produces **coverage**, not edits. That constraint is what prevents scope explosion.

**How the three connect (and why that's all for v0.1):**

```
              ┌─────────────────────────────┐
   CHANGE ────┤ deslop → sweep-the-class     ├──── an incident?
              └─────────────────────────────┘         │
                                                      ▼
                                                  a LESSON
                                                      │
                                          applies to the next project
```

Three components, one loop, no engine.

# LESSONS LEDGER

The foundation. Report 08 identified this as the largest gap and the cheapest fix.

## What qualifies as a lesson

All four must hold:

1. **It cost something real.** Time, a bug, an outage, a revert, a re-filed issue. If nothing was lost, it's a preference.
2. **It would be true in a different repository**, given the same condition.
3. **It isn't discoverable in 30 seconds** from the code, the docs, or the error message.
4. **It changes what an agent does**, not just what it knows.

Test 4 is the sharpest and the one to apply hardest. *"Supabase returns `{ data, error }`"* is a fact — it changes nothing. *"A destructured `error` that is never read makes a failure look like an empty result; on read paths, throw"* changes the next line of code someone writes.

## What does not qualify

| Not a lesson | It's actually a… | Example |
|---|---|---|
| Always true, no condition | RULE → central `AGENTS.md` | "Never commit secrets" |
| True only in one repo | PROJECT CONTEXT → project `AGENTS.md` | "This project's colours live in `globals.css` `:root`" |
| Restates the library's own docs | Nothing | "Next.js App Router uses `page.tsx`" |
| A preference with no cost | Nothing | "I prefer kebab-case filenames" |
| A one-off with no generalisable condition | Commit body | "The RPC wasn't pushed to prod that day" |
| A fix without a shape | An issue | "Fixed the checkout bug" |

**Hard cap: if the ledger passes ~30 entries, you are logging, not learning.** Apply test 4 harder before adding more.

## Where lessons live

```
personal-agent-system/lessons/*.md      ← canonical, flat, no subfolders
```

**Challenged and rejected:** category subfolders (`lessons/nextjs/`, `lessons/windows/`). With 9–30 entries a taxonomy adds navigation cost and duplicates what `applies-to` already expresses — and a lesson tagged `[nextjs, windows]` has no correct folder. Flat with frontmatter wins until the ledger is large enough to browse rather than grep, which it won't be.

## What a lesson contains

```markdown
---
applies-to: [nextjs, windows]
discovered: 2026-07 (hotsauce-mama)
status: unverified-since next@16.2.10
---

# next/og ImageResponse breaks `next build` on Windows

`next/og`'s `ImageResponse` (the `app/icon.tsx`, `app/opengraph-image.tsx`
conventions) hit a Windows-only bug in `@vercel/og`'s bundled default font
loader — `TypeError: Invalid URL` — that broke `next build` locally while
building fine on Linux CI and Vercel.

**Cost:** a local build failure that looks like a project problem and isn't,
on a machine where CI is green.

**Instead:** static SVG/PNG icons and metadata-based OG images. These work
identically on every OS regardless of whether the bug is still live.

**Strongest rung available:** none — this is judgement. Prose is correct here.
```

Four frontmatter-and-body elements, each earning its place:

| Element | Why it exists | Consumed by |
|---|---|---|
| `applies-to` | The scope predicate. **This is what makes a lesson portable rather than global noise.** | Project init — matched against detected stack |
| `discovered` | Staleness judgement. A 2026 lesson about Next 14 may not hold on Next 18. | A human reading it |
| `status` | `active` \| `unverified-since <version>` \| `superseded by <slug>` | A human reading it |
| **Cost** | Test 1 made explicit. Forces honesty about whether it qualifies. | You, when tempted to add a preference |
| **Instead** | Makes it actionable. A lesson without an "instead" is a complaint. | The agent |
| **Strongest rung** | A standing backlog of structural encodings. | Future you; later, the dreaming layer |

**Note on "strongest rung."** Report 02 §3 proved you already convert incidents into mechanisms (the Playwright suite, `guard-main-base.yml`, the RLS CI assertion, the pinned `setup-cli`) — but only when the failure hurt. This line makes the option visible every time, without forcing it. For the `next/og` lesson the honest answer is "none"; for the Supabase-error lesson it's "an ESLint rule on unused destructured `error` bindings — not yet written."

## How a lesson is created

**v0.1: by hand, from `templates/lesson.md`.** No skill required.

This is deliberate. A `capture-lesson` skill is convenience; the template is the mechanism. Building the skill first would make the ledger depend on skill installation working (Q3's unresolved risk) and would let you avoid deciding what a good lesson looks like. Write six by hand, then automate the shape you actually converged on.

**Trigger, stated as a rule in central `AGENTS.md`:** *"When something surprised you or cost you time and the cause wasn't in this repo, write a lesson before moving on."*

## How a lesson is discovered

Two mechanisms, and the difference between them is the crux of the design.

**Primary — inline at project start.** Match `applies-to` against the detected stack and **copy the relevant lessons into the project's `AGENTS.md`**, each tagged with its slug and date:

```markdown
## Inherited lessons

<!-- from personal-agent-system/lessons -->
- **next-og-imageresponse-windows** (2026-07): don't use `next/og`'s
  `ImageResponse`; it breaks `next build` on Windows. Use static icons.
- **shadcn-pin-tailwind-v3** (2026-07): pin `shadcn@2.10.0`. `@latest`
  emits Tailwind-v4-only CSS and Base UI primitives.
- **supabase-error-must-be-checked** (2026-07): always read the `error` from
  a `{ data, error }` result. On read paths, throw; a failure must never look
  like an empty result.
```

**Secondary — on demand.** Central `AGENTS.md` says the ledger exists and where. An agent hitting an unfamiliar technology can grep it.

### Why copy rather than reference — the key decision

**TRADEOFF.** A reference (`see personal-agent-system/lessons/`) never goes stale, but requires the central repo to be present *and* the agent to think to look. A copy is always in context but can drift from the canonical version.

**DECISION: copy.** Two reasons, both grounded:

1. *[PROVEN]* Report 08 established that your entire cross-project knowledge problem is that nobody looks. `~/.claude/` was empty of durable instruction; nine lessons sat in one repo while a sibling project on the identical stack repeated the conditions. A mechanism that depends on remembering to look has already failed once here.
2. *[INFERRED]* An inlined lesson costs ~2 lines of project `AGENTS.md`. Three or four of them is ~8 lines. That is affordable in any project, including the 5-commit ones.

**Drift is handled by the slug + date marker**, which makes a future `lesson-sync` check possible without building it now: grep projects for `**<slug>** (<date>)`, compare against `lessons/<slug>.md`'s `discovered`. That capability costs nothing today and is not foreclosed.

## How stale lessons are handled

Three states, mirroring practice already visible in your `CLAUDE.md` (*"Not re-verified against 16.2.10 … re-check whether this bug still reproduces before assuming this note is current"*):

| State | Meaning | Action |
|---|---|---|
| `active` | Believed current | Inline freely |
| `unverified-since <version>` | Was true; conditions may have changed | Inline, but the text says to re-check before relying on it |
| `superseded by <slug>` | Proven false or replaced | **Never inline. Never delete.** |

**Never delete a superseded lesson.** The reason you believed it, and what proved it wrong, is itself a lesson — and deleting it means re-learning the same thing. This mirrors your own practice: you documented the "SOUCE" label typo and its pixel-patch script as *"historical only"* rather than removing the note.

## The nine known lessons — triage, not bulk import

You said not to dump all nine in. Applying the four-part test:

| Candidate | Verdict |
|---|---|
| Git Bash rewrites POSIX-looking args into Windows paths | **RULE, not lesson.** Unconditionally true on this machine, for every project, every tool. → central `AGENTS.md`. It already corrupted issue #223's title. |
| No Docker on this machine | **RULE.** → central `AGENTS.md`, as a verification-honesty constraint. |
| `next/og` `ImageResponse` breaks `next build` on Windows | **LESSON** — `[nextjs, windows]` |
| Pin `shadcn@2.10.0`; `@latest` emits Tailwind-v4-only CSS | **LESSON** — `[shadcn, tailwind-v3]` |
| A client Zod schema is not server-side validation for a Server Action | **LESSON** — `[nextjs, server-actions]` |
| Always check the `error` from a `{ data, error }` client | **LESSON** — `[supabase, postgrest]`; the highest-value entry in the ledger |
| An external call after a state-changing write needs a compensating cleanup | **LESSON** — `[stripe, payments, inventory]` |
| `next dev` doesn't replicate ISR caching | **LESSON** — `[nextjs]` |
| `supabase/setup-cli@latest` hits GitHub's release API rate limit | *Defer.* Narrow (one action), and the fix is already applied in the only repo affected. Add it if it recurs. |
| Unit tests need Supabase unconfigured; e2e needs it configured | *Defer.* Genuinely project-shaped — it's about *your* test layering, not a portable truth. → project context. |

**Result: 2 rules, 6 lessons, 2 deferred.** Six is a good starting ledger — enough to prove the mechanism, small enough to read in one sitting.

# DESLOP

Full prior specification: `reports/09_DESLOP_DESIGN.md`. Restated here as the conceptual v0.1 spec, with the archaeology findings made structural rather than advisory.

## Scope

**For AI-generated or AI-assisted changes only.** Not a linter, not a code reviewer, not a refactoring tool, not a bug finder. If it starts finding bugs, it hands off.

## The fundamental question

> **Would this line exist, in this file, if a careful author familiar with the surrounding code had written it?**

Deliberately *not* "is this good code". Report 04 established your conventions are already strong and highly specific; "good code" invites an external ideology to overwrite them. The question above is answerable from the file itself.

## The three-gate model

A line is removed only if **all three** gates pass. This is the structural encoding of the report 09 findings.

```
GATE 1 — SCOPE       Is it in the diff against the base?
                     Untouched code is out of scope, however bad.

GATE 2 — CONSISTENCY Is it inconsistent with this file's own conventions,
                     inferred from the file and 2-3 siblings?
                     The local file always beats any global preference.

GATE 3 — LOSSLESS    Does removing it lose INFORMATION, SAFETY, or INTENT?
                     If yes → do not remove. Report instead.
```

Gate 3 is the whole adaptation. It is what makes this safe for your codebase.

## Gate 3, expanded — the three things never removed

**INFORMATION.** A comment that says what code cannot: where this came from, what broke here before, what the obvious alternative costs, why a suppression is legitimate.

> *[PROVEN, report 04 §4]* Your comments are ~10% of lines and almost entirely of this kind. Real examples that a naive pass deletes: *"was duplicated across edit-price-form.tsx, edit-shipping-zone-rate-form.tsx, and admin-shipping-zones.ts before being centralized here"*; *"Pinned rather than 'latest' — resolving 'latest' … hit a rate limit and failed CI outright (2026-07-17)"*.

Mechanical guard: never remove a comment containing an issue reference, a date, a file path, or the words *found*, *incident*, *instead*, *because*, *was duplicated*.

**SAFETY.** Anything that makes a failure visible, or undoes a partial write.

> *[PROVEN, report 03 Problem 1]* Insufficient error handling is your #1 recurring production bug class — 11 references across two projects and two languages. You have 31 `try` blocks in 24,856 lines; you are at the floor, not above it. The upstream instruction to remove "defensive checks or try/catch blocks abnormal for trusted code paths" points the wrong way here.

**The failure-visibility clause.** On encountering a `catch`, a swallowed error, or a generic failure return, ask first: *can the caller distinguish failure from an empty or successful result?*

- **No** → this is not slop, it is Problem 1. **Do not remove.** Report it, recommend making failure visible.
- **Yes, and the block adds only a `console.error`** → slop. Propose replacing with the local pattern (throw on read paths, discriminated result on write paths). **Replace, never delete.**
- Wraps an external call following a state-changing write → **load-bearing, never touch.** Your `CLAUDE.md` documents exactly this pattern.

**INTENT.** A deliberate choice recorded anywhere — a justified suppression, a pinned version, an explicit `unknown` generic, a null-safe config guard that exists so tests can run unconfigured.

## What deslop actually removes

Ordered by confidence, all drawn from measured evidence in your own repos (report 03 Problem 10):

1. **Patterns you never write, appearing in a diff.** *[PROVEN, report 04 §13]* Your recent code contains no barrel files, no TS classes, no arrow-function components, no global-state libraries, no inline hex, no inline user-facing strings, no inline magic numbers, no commented-out code. Any of these in a diff is inconsistent by definition. **Highest confidence, lowest cost.**
2. **Comments restating the next line** — `// Add security headers`, `// Prevent clickjacking`, `// Validate file type`.
3. **Banner and tutorial-voice comments** — `/** APPLICATION CONSTANTS / This prevents "magic numbers" scattered throughout the code */`.
4. **Commented-out scaffold** — the ~15 lines of generator output left in `fitnessTracker/playwright.config.ts`.
5. **Uniform catch-log-return-generic** — via the failure-visibility clause above, so this is a *replacement*, not a deletion.
6. **Aspirational prose** — `// In production, you'd use a service like SendGrid, Mailgun, or AWS SES`.
7. **Inline strings / colours / numbers** that the project has a home for.
8. **Nesting a guard clause would flatten.** Rare — you already write guard clauses.

**Removed from the upstream skill entirely:** the `any` clause. *[PROVEN]* Zero occurrences in 24,856 + 9,389 lines. A dead clause is not harmless — it teaches the model that this skill's criteria don't match reality.

## Output

Two sections, always:

```
Deslopped 4 hunks across 3 files. Removed 6 comments restating adjacent code,
one commented-out config block, one inline hex belonging in globals.css.
Typecheck and tests pass.

Left alone (flagged, not changed):
- src/lib/reports.ts:42 — catch swallows a failed query and returns []. Silent-
  failure risk, not slop. Recommend making the failure visible.
- src/lib/import.ts:18 — `(row: any)` at a JSON.parse boundary. This is an
  unvalidated trust boundary, not lazy typing. Parse it instead of annotating it.
```

The second section is what makes it trustworthy enough to run unsupervised, and it is where the Q5 coverage principle applies.

## Guardrails

- Diff-only. No behaviour change. No API/signature changes, no renames, no file moves.
- No architectural change, no re-abstraction, no cross-file consolidation.
- Never remove error handling — only replace with the local pattern, and only when failure stays visible.
- Never impose a style the surrounding files don't already demonstrate.
- **When uncertain, leave it and say so.**
- Verify: run the project's typecheck and tests; report if they fail.

## Verification

`git diff` after the run contains only deletions and comment rewrites; typecheck and tests pass; no removed line matches the mechanical guard above. The last check is a grep and should be run by the skill on itself.

# SWEEP-THE-CLASS

## The fundamental question

> **Did I fix the instance, or did I fix the class?**

## Why this is the highest-leverage missing skill

*[PROVEN, report 03 Problem 2]* You have documented, in your own tracker, three cases where a closed fix wasn't complete:

- Issue #192 — *"list-customers.ts and analytics.ts still do the unbounded full-table-scan closed issue #121 said was fixed"*
- Issue #250 — *"Silently swallowed Supabase errors … (same class as #180/#249)"*
- Issue #131 — *"PR #127's fix doesn't work as intended"*

And PRs whose titles are literally counts of sites missed the first time: #171 (3 admin pages), #252 (10 read paths), #206 (3 copies), #103 (12 files). One of these reached a customer: PR #249, an in-stock product showing "Coming Soon" on one route and "Available Now" on another.

*[PROVEN, report 06 §4]* No equivalent exists in any of the 158 external skills reviewed.

## Trigger

- A fix is about to be declared done
- You say "where else", "same class as", "sweep"
- Chained: `deslop` and any fix-type work recommend it before completion
- An issue is filed that reads like it has siblings

## Input

- The fix just made — a diff, a commit, or a description
- Optionally, the issue that prompted it

## Discovery process

**1. Characterise the shape.** Derive two things, both required:

| | What it is | Why required |
|---|---|---|
| **Mechanical signature** | A concrete, runnable search — a grep pattern, a symbol, a call site, an import | Without it the sweep is a semantic scan of the whole repo, which is where scope explosion comes from |
| **Semantic condition** | What makes a match a *real* instance rather than a lookalike | Without it the mechanical signature over-matches and the output is noise |

*Worked example (#250):*
- Mechanical: files destructuring `{ data, error }` from a Supabase call
- Semantic: …where `error` is never read before `data` is used, **and** the caller cannot otherwise distinguish failure from an empty result

**2. Stop if the shape isn't expressible.** If no mechanical signature exists — as with #189's Postgres `FOR UPDATE` + `LIMIT` interaction — say so and stop. Report: *"This defect's shape is semantic and cannot be searched mechanically. A targeted review of <N named files> would be needed. Not performed."* **An honest stop is a valid outcome.** This is the primary defence against scope explosion.

**3. Define and state the search scope** before searching. Default: the directories that contain the original defect plus their siblings at the same layer. Not the whole repo by default.

## Coverage check

Every candidate gets one of three verdicts, and every verdict is recorded:

| Verdict | Meaning | Recorded? |
|---|---|---|
| **same-class** | Genuinely the same defect | Yes — with a fix/defer recommendation |
| **similar-not-same** | Matches mechanically, differs semantically | Yes — with the distinguishing reason |
| **false-positive** | Matched the pattern, isn't relevant | Yes — with why |

Recording exclusions is what stops the next sweep re-litigating the same candidates. It is also what makes a null result informative (Q5).

## False positive handling

The semantic condition is the filter. When a candidate matches mechanically but not semantically, the output states the distinguishing fact — *"`getBrandConfig` destructures `error` but returns a typed default that the caller checks; failure is distinguishable"*. If you disagree with an exclusion, that disagreement is a correction worth capturing as a lesson.

## Output

```
CLASS:   Supabase read paths where a failed query is indistinguishable from
         an empty result.
PATTERN: `{ data, error }` destructured, `error` never read (grep + read).
SCOPE:   src/lib/**, src/app/actions/** — 42 files.

FOUND: 13 candidates → 10 same-class, 2 similar-not-same, 1 false-positive.

SAME-CLASS (10)
  src/lib/commerce/storefront.ts:43   getCommerceProductBySlug   fix now
  src/lib/locations.ts:27             getAllStockists            fix now
  ... (8 more)

SIMILAR, NOT SAME (2)
  src/lib/journal.ts:18   returns a typed default the caller checks — distinguishable

FALSE POSITIVE (1)
  src/lib/brand.ts:9      not a Supabase call; matched on shape only

COVERAGE: 42 of 42 files in scope searched. Not searched: src/components/**
          (no data access), supabase/migrations/** (SQL, different shape).
```

**No edits.** The output is an inventory and a set of decisions.

## Guardrails

- **Never edits.** Hard constraint, and the primary anti-scope-explosion mechanism.
- Never widens the shape until it matches everything. If the pattern stops discriminating, the shape was wrong — say so and re-derive.
- Never sweeps outside the stated scope without saying so.
- **Systemic escape hatch:** if same-class sites exceed ~20, stop and report *"this is systemic, not a set of instances"*. That is an audit finding, not a sweep, and it belongs in an issue.
- Always states what was searched, including what was excluded and why.

## Validation

1. Every listed site carries a verdict and a reason
2. The search performed is stated concretely enough that you could re-run it
3. The coverage line names what was *not* searched
4. Zero files were modified

# PORTABILITY MODEL

## Two layers. Not three, not five.

```
GLOBAL   personal-agent-system/        installed once per machine
  ├── AGENTS.md          RULES         always true, no conditions
  ├── lessons/*.md       LESSONS       true when applies-to matches
  └── skills/*/SKILL.md  SKILLS        how to decide

PROJECT  <any repo>/                   ~8 lines to adopt
  ├── AGENTS.md          CONTEXT + PROJECT RULES + INHERITED LESSONS
  └── CLAUDE.md          @AGENTS.md
```

**That is the entire portability model.** No `.agent/` directory, no config, no manifest, no selected-skills list.

## The invariant

> **The global layer supplies how to decide. The project layer supplies what is true here.**

This is what satisfies your requirement that a project inherit capability without inheriting foreign assumptions. A skill that hardcodes "components are kebab-case" breaks on `senus-board-report` (PascalCase). A skill that says "match the local convention, and prefer `AGENTS.md` when explicit" works in both. *[PROVEN, report 04 §1]* — your two serious projects genuinely differ here, so this isn't hypothetical.

## What each layer may and may not contain

| | Global | Project |
|---|---|---|
| Rules with no condition | ✅ | — |
| Rules true only here | — | ✅ |
| Lessons (conditional, portable) | ✅ canonical | ✅ inlined copy, slug + date |
| Architecture, decisions, design system | — | ✅ |
| Skills | ✅ | — |
| Style profile | — | ✅ (~15 lines) |
| Runbooks | — | ✅ (`README.md`) |

**The routing rule:** *anything that would be true in your next project belongs global; everything else stays local.* Report 08 showed nine items sitting in the wrong column.

## Adoption — the Era-2 test

What it takes to bring this to a new project:

```
1. Copy templates/project-AGENTS.md  →  AGENTS.md          (~30 lines)
2. Add: echo '@AGENTS.md' > CLAUDE.md                       (5 bytes)
3. Inline lessons whose applies-to matches the stack        (~8 lines)
```

Under five minutes, no tooling required, works on a 5-commit brochure site and on `hotsauce-mama` alike. Step 3 is scriptable later; doing it by hand first is how you find out whether the `applies-to` vocabulary is right.

**Skills need no per-project step at all** — they install once per machine and are available everywhere. That is why `selected-skills.yml` was rejected in report 13: there is nothing to select.

# IMPLEMENTATION ORDER

Your guessed order — lessons, sweep, deslop — is **correct**, but for a sharper reason than "lessons are foundational". The three are functionally independent; the ordering is by *value now ÷ cost to build safely*.

## 1. Lessons ledger + `AGENTS.md` + templates

**Why now.** It is the only component whose value *decays with delay*. Report 08 identified nine lessons from two projects in one afternoon; each project you ship without the ledger buries more, and you will not remember the next nine. It also has zero dependencies — no skill installation, no harness, no tooling. It works if everything else fails, which de-risks Q3.

**Dependencies.** None.

**Done means.**
- `templates/lesson.md` exists and six lessons are written against it
- Central `AGENTS.md` holds the two rules (Git Bash path mangling, no-Docker verification honesty) plus the verification-honesty rule
- `templates/project-AGENTS.md` exists with an "Inherited lessons" section
- `README.md` lists the six lessons with one line each

**How tested.** *The adoption test:* take any existing repo you didn't design this against — `achara-dublin-website` is ideal (Next.js, 5 commits, no tests) — and adopt it. Time it. **If it takes more than five minutes or produces more than ~40 lines, the design is too heavy and should be cut before proceeding.** That is a real pass/fail gate, not a formality.

## 2. `sweep-the-class`

**Why now, and before deslop.** Highest leverage in the entire library (report 05: 27/29). Pure procedure — no fixtures needed, because it never edits, which is also why it's cheap to build safely. And it is uniquely testable against known ground truth.

**Dependencies.** None functionally. Benefits from step 1 existing so that corrections found while using it have somewhere to go.

**Done means.**
- `SKILL.md` specifies the two-part shape (mechanical + semantic), the three verdicts, the coverage statement, and the systemic escape hatch
- Guardrail "never edits" is stated as a hard constraint
- Output format matches the worked example above

**How tested.** The retrospective test, which has a known answer:
- Check out `hotsauce-mama` before PR #252, describe the #180 fix, run the sweep. **Target: finds ≥8 of the 10 read paths PR #252 fixed, with no more than 2 false positives.**
- Repeat for #121 → #192 (the unbounded-query thread). **Target: finds `list-customers.ts` and `analytics.ts`** — the two files issue #192 says were missed.

If it fails these, the shape-characterisation step is wrong and needs work before the skill is trusted. This is the strongest acceptance test in the whole design.

## 3. `deslop`

**Why third, not first.** It is the one skill that *edits your code*, and report 12 established the asymmetry: a false positive deletes information that cannot be recovered and destroys your trust in the skill permanently. That makes the fixture set a prerequisite, not a nice-to-have — and building the fixtures is most of the work.

**Dependencies.** The `should-not-flag` fixture set. Non-negotiable.

**Done means.**
- `SKILL.md` implements the three-gate model with Gate 3 explicit
- `reference/slop-patterns.md` holds the pattern catalogue (keeps `SKILL.md` short)
- `tests/should-not-flag/` contains **at least seven real hunks from your own repos**, listed in report 12 §2: the `format.ts` provenance comment, the `ci.yml` setup-cli pin note, the `locations.ts` #250 consequence comment, the `meta-pixel.tsx` justified suppression, the `checkout.ts` compensating try/catch, the `useServerAction` `unknown[]` generic, an `isSupabaseConfigured()` guard
- `tests/should-flag/` contains real hunks from `invoiceToSheet`, `kitchenapp`, `fitnessTracker`
- `tests/ambiguous/` contains at least the catch-that-hides-failure and the untyped-`JSON.parse` cases

**How tested.**
- `should-not-flag`: **100%. Non-negotiable.** A single false positive here blocks release.
- `should-flag`: ~80% is fine. A miss costs one round of surviving slop.
- `ambiguous`: must **flag and hand off**, must **not** auto-fix. This tests the failure-visibility clause, which is the clause protecting you from your #1 bug class.

**Then stop.** Use all three for a month before adding anything. The core argument of report 05 is that leverage concentrates in a handful of skills; adding more before these prove themselves is exactly how a library becomes a junk drawer.

# FUTURE COMPATIBILITY

v0.1 must not foreclose the eventual loop:

```
WORK → EXPERIENCE → LESSON → PATTERN → DREAMING → PROPOSAL → APPROVAL → SKILL
```

What v0.1 does to keep that open, at zero extra cost:

| Future need | Preserved by |
|---|---|
| **A mineable experience corpus** | Git commit bodies + PR descriptions, which you already write in a consistent shape. One rule in central `AGENTS.md` keeps the habit explicit. No new machinery. |
| **Structured lessons to detect patterns over** | `applies-to`, `discovered`, `status` are machine-readable from day one. Six lessons is a small corpus but a *correctly shaped* one. |
| **A standing backlog for dreaming's first proposals** | The "strongest rung available" line in each lesson. Every lesson whose rung is stronger than "prose" is a concrete, pre-justified proposal waiting to be built. |
| **Human approval as the default** | Nothing in v0.1 auto-applies. Sweep never edits. Deslop edits only through three gates and reports what it left alone. The approval gate exists because it's the default, not because it was engineered. |
| **Staleness detection across projects** | The slug + date marker on every inlined lesson makes a future `lesson-sync` a grep, not a rewrite. |
| **Evaluation of whether skills worked** | The metric already exists in your practice: issues that say *"same class as #X"*. If that count goes to zero after `sweep-the-class`, it worked. No instrumentation needed. |

**The one thing that would foreclose the future:** letting lessons become free-form prose without `applies-to`. A ledger of untagged paragraphs cannot be matched to a project, cannot be checked for staleness, and cannot be mined. The frontmatter is three fields precisely because it is the minimum that keeps the future open.
